# Contributing

These conventions apply to every georg repository. A repository may extend them in its own `CONTRIBUTING.md`.

## Language

**Everything is written in English:** documentation, code comments, commit messages, pull requests, issues, and every identifier (functions, parameters, variables, types, files, CSS classes, tokens).

User-facing copy may be localized, but it must live in translation files, never hard-coded in another language.

## Code standards

We follow [Clean Code](https://www.oreilly.com/library/view/clean-code-a/9780136083238/) principles and common open-source practice:

- **Intention-revealing names.** `remainingMilliseconds`, not `ms`; `inbox`, not `ib`. Booleans read as questions: `isExpired`, `hasAttachments`, `canSend`.
- **Small functions that do one thing.** If a function needs a comment to explain its sections, split it.
- **No magic values.** Name constants: `MIN_TEXT_CONTRAST = 4.5`, not a bare `4.5`.
- **Comments explain why, not what.** The code says what it does; comments record intent, constraints and trade-offs.
- **No dead code.** Delete it; git keeps the history.
- **Fail loudly.** Validate inputs at boundaries and throw clear errors; never swallow exceptions silently.
- **Consistency over preference.** Match the style of the surrounding code; formatting is enforced by tooling, not reviews.
- **Tests for behavior.** New behavior comes with tests; bug fixes come with a regression test.
- **Security by default.** No secrets in the repository, validate untrusted input, and treat external content (emails, files, model output) as untrusted.

## Branches

The default branch is **`main`**.

| Branch | Purpose |
| --- | --- |
| `main` | Reference code. Changes land through pull requests. |
| `feat/<short-description>` | New functionality, branched from `main`. |
| `fix/<short-description>` | Bug fix, branched from `main`. |
| `chore/<short-description>` | Configuration, dependencies, tooling, CI. |

## Commits

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>[optional scope]: <description>

[optional body]

[optional footer]
```

| Type | When to use it |
| --- | --- |
| `feat` | New functionality |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `style` | Formatting, no logic change |
| `refactor` | Restructuring without a feature or fix |
| `test` | Adding or fixing tests |
| `chore` | Build, tooling, dependencies |
| `ci` | CI/CD configuration |
| `perf` | Performance improvement |

Breaking changes use `!` after the type and a `BREAKING CHANGE:` footer.

## Pull requests

1. Branch from `main`.
2. One topic per pull request.
3. Fill in the pull request template.
4. Wait for CI and the security scan to be green before requesting review.
5. Squash merge, so `main` keeps one commit per pull request.

## Versioning

We follow [Semantic Versioning](https://semver.org/) and record every user-visible change in [`CHANGELOG.md`](CHANGELOG.md) ([Keep a Changelog](https://keepachangelog.com/) format). A release is a `vX.Y.Z` tag matching `MARKETING_VERSION` in `project.yml`, published as a GitHub release with the signed and notarized disk image.

## Security

Never commit secrets, `.env` files, keys or certificates. Every repository runs gitleaks and semgrep in CI, and GitGuardian monitors the organization. To report a vulnerability, see [`SECURITY.md`](SECURITY.md).

## georg-md extensions

### Swift and the generated project

- The Xcode project is generated by XcodeGen from `project.yml` and never committed. Run `make project` (or any `make` target) after adding, moving or renaming files.
- Swift uses 4-space indentation (`.editorconfig`). The app and dev tool targets compile in Swift 5 language mode; keep code free of new warnings.
- Formatting is not enforced by a tool yet: match the surrounding code.

### Tests

`make test` builds `GeorgDevTool` and runs the suite in `Tools/DevTool/LiveChecks.swift`: source map conversion, the Write mode styler (including partial-versus-full restyle equivalence under random edits), hostile documents, edit helpers, nesting limits, the highlighter and the update check. A behavior change adds a check there; a bug fix adds a regression check. Visual changes are verified with the dev tool's screenshot tasks (`live`, `code`, `settings`, `pdf`) in light and dark themes.

### Untrusted input

Markdown files, inline HTML, images, links, Quick Look requests and GitHub API responses are untrusted. Keep the invariants in `AGENTS.md` ("Security invariants"); a change that relaxes one needs an explicit reason in the pull request.

### Brand assets

The app icon and any brand mark come from a pinned georg-ds release (`make icon`), are never redrawn or recoloured here, and are recorded in [`CREDITS.md`](CREDITS.md).

### Reference material

`rscs/` (git-ignored) holds third-party reference material such as other apps and screenshots. It is design reference only: never copy code or assets from it, and never commit it.
